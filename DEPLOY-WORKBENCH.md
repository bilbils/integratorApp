# Deploying the Architecture Workbench

**Staged 2026-08-22. Build stamp `0822-2153`. Nothing here has been pushed, deployed or applied.**

The workbench becomes a page on the site you already have, signing in with the auth you already
have, writing rows to the database you already have. No new host, no new vendor, no new bill.

```
josh → staffility-integrator-mockup.netlify.app/workbench
     → [Netlify site password]          the shared gate — already on
     → the page                          web/public/workbench/index.html
     → POST /api/v1/auth/login           EXISTS. admin_users + JWT
     → GET/PUT /api/v1/plan/*            NEW
     → plan_jobs · plan_answers          NEW, migration 010
```

---

## Two corrections worth having in your head first

**Supabase Auth is not what this app uses.** `auth.users` is **0 rows** — verified. The Integrator
has its own auth: `admin_users` (email + bcrypt) and a JWT from `POST /api/v1/auth/login`. Josh does
not need "a Supabase password." He needs **one row in `admin_users`**, which step 3 creates.

**The browser cannot talk to Supabase directly, by design.** RLS is on for all nine tables with
**zero policies** — migration 002 deliberately closing the PostgREST/anon door. A page using the
publishable key would read nothing at all. So the page goes through the API, which connects as the
table owner and bypasses RLS. That is the existing, proven path and it is the right one.

## Steps

### 1 · Put the files in the clone

They are staged under `stage/` in the outputs bundle, in repo-relative layout. Copy the tree over
`C:\dev\project\integratorApp`, then read the diff in GitHub Desktop before anything else.

I could not do this myself: the clone is not connected to the session, and running git through the
device bridge leaves an undeletable `.git/index.lock` that blocks your push. Connect
`C:\dev\project\integratorApp` next time and I can stage directly into it.

### 2 · Apply the migration

**Nothing runs migrations automatically.** Render's `buildCommand` is `npm ci --include=dev &&
npm run build` — build only. Confirmed by reading `render.yaml`; this was an open question and the
answer is no. So:

```powershell
npm --prefix api run migrate
```

Against the live `DATABASE_URL` — the session pooler on 5432. It replays every file including
010; that is expected and safe.

Then read it back rather than trusting the output:

```sql
select table_name from information_schema.tables
 where table_schema = 'public' and table_name like 'plan_%';
```

Two rows, or it did not work.

### 3 · Give Josh an account

```powershell
$env:ADMIN_EMAIL='josh@…'; $env:ADMIN_PASSWORD='…'; npm --prefix api run add-admin
```

**Not `npm run seed`** — that rotates the consumer key unconditionally on every run and has already
invalidated a live key once (§ NEVER #3). `add-admin` touches `admin_users` and nothing else.

Single-quote the password in PowerShell: double quotes interpolate `$`. The script never prints the
password, not even redacted — it prints the hash *length*, which confirms the write without putting
the value on your screen. Send it to Josh over something that is not email or chat.

### 4 · Push

Review the diff, commit to a branch, push in GitHub Desktop. Push to `main` **is** the deploy, to
both hosts at once. I have not pushed and will not.

### 5 · Wait for both halves

Netlify rebuilds the site; Render rebuilds the API. Both must finish.

### 6 · Confirm the deploy actually landed — the check that can fail

```powershell
curl.exe https://integrator-api-koyz.onrender.com/health
```

Expect `"build":"0822-2153"`. This is why all three stamps moved together: if `/health` still says
`0808-1816`, Render has not picked it up. **Do not check this against the netlify.app origin** — the
visitor-password gate answers 401 before the proxy runs, and a check whose success criterion is 401
cannot fail (§ NEVER #1).

Then open `https://staffility-integrator-mockup.netlify.app/workbench`, hard-refresh
(Ctrl+Shift+R), and sign in.

### 7 · Load the catalogue

The page offers it on first open, once, only while the table is empty. Seeding refuses outright if
there are already rows — the failure it exists to prevent is someone re-seeding mid-session and
flattening what was agreed in the room.

## What Josh does

One link. The **site password** first (that is the shared one — send it separately), then **his own
email and password**. That is two gates on purpose: the site password keeps the page off the open
web, and the login is per-person so the rows say who changed what.

If you would rather drop the site password and rely on the login alone, turn it off in Netlify →
Site configuration → Access & security. Read § NEVER #1 first: that gate is currently the reason a
401 from that origin means nothing, and removing it changes what your own checks are testing.

---

## Honest limits

- **Two people editing the same job within a few seconds is last-write-wins.** Different jobs never
  collide — that is the whole reason for rows over one document — but the same row has no lock. The
  row shows who touched it and when, which is the right amount of protection for a two-person tool
  and not a substitute for one you would put in front of a customer.
- **The poll is 20 seconds**, paused while the tab is hidden. The other person's change is not
  instant.
- **The session is `sessionStorage`** — closing the tab signs you out. Deliberate.
- **The plan tables are operator data in a control plane** that has ruled it does not take custody of
  consumer data. The same asterisk already sits on `session_highlights`. Worth a decision, not an
  accident.
- **`access_grants` is still not enforced anywhere.** Unchanged by this work, and it stays the thing
  to fix before any second client has a key.

## Rolling it back

`git revert` the commit and push. The tables can stay — nothing else reads them, and dropping them
throws away the plan. If you really want them gone:

```sql
drop table if exists plan_jobs, plan_answers;
```

and delete `010_plan.sql` from the repo in the same commit, or the next `migrate` puts them back.
